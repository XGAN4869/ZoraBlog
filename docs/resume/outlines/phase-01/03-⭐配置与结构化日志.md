# 03 · 配置与结构化日志

目标：**让端口、运行环境和数据库地址来自环境变量，并且日志不泄露密码。**

这一篇先建立配置模型。MySQL 真正连接放在下一篇。

## 本篇先建立一条因果链

不要把这一篇理解成“创建一个 `Config` 结构体”。真正要解决的是：**同一份程序怎样在不同环境中使用不同参数，同时不把密码写进源码。**

```text
PowerShell / Compose / 服务器
        ↓ 注入环境变量
config.Load()
        ↓ 校验并生成 Config
cmd/server/main.go
        ├─ 用 Port 启动 HTTP
        ├─ 用 DatabaseDSN 创建数据库连接
        `─ 用 Environment 选择日志格式
```

如果没有这一层，端口、密码和运行环境就会散落在 `main.go`、数据库代码和 Docker 配置中。以后换服务器时，你无法判断到底应该修改哪一处。

本篇学完后，你应该能自己回答：

- 环境变量在什么时候进入 Go 程序？
- `Config` 为什么不直接读取数据库？
- `.env.example` 为什么可以提交，`.env` 为什么不可以？
- 为什么日志能记录端口，却不能记录完整 DSN？

## 1. 环境变量解决什么问题

开发电脑、测试环境和服务器使用不同的数据库地址。如果把地址写死在 Go 源码里，每换环境就要改代码并重新编译。

环境变量让“程序逻辑”和“运行参数”分开：

```text
程序逻辑：怎样连接数据库
运行参数：这一次连接哪台数据库
```

`.env.example` 只展示变量名称和开发示例，真实密码不能提交到 Git。

## 2. 先写配置测试

计划创建：

```text
backend/internal/config/config.go
backend/internal/config/config_test.go
```

配置结构：

```go
type Config struct {
	Environment string
	Port        string
	DatabaseDSN string
}
```

逐个看字段的职责：

- `Environment` 不是给用户看的文案，而是告诉程序当前处于开发还是生产环境。后面会据此选择文本日志或 JSON 日志。
- `Port` 使用字符串，是因为最终要拼成 `":" + cfg.Port` 交给 HTTP 服务器；此时不需要参与数学运算。
- `DatabaseDSN` 是数据库连接说明。它包含协议、账号、密码、地址、库名和连接参数，因此属于敏感信息。

`Config` 只保存已经校验过的结果。其他模块应该接收 `Config` 或其中某个字段，而不是每个模块都重新调用 `os.Getenv`。否则同一个变量可能在不同地方拥有不同默认值，比如server模块port 是8080，db是3306。

测试至少覆盖：

1. `APP_ENV` 和 `PORT` 未设置时使用开发默认值。
2. `DATABASE_DSN` 缺失时返回明确错误。
3. 设置全部变量时原样读取。

测试中使用 `t.Setenv`，不要修改真实系统环境。

```go
func TestLoadRejectsMissingDatabaseDSN(t *testing.T) {
	t.Setenv("APP_ENV", "development")
	t.Setenv("PORT", "8080")
	t.Setenv("DATABASE_DSN", "")

	_, err := Load()
	if err == nil {
		t.Fatal("expected missing DATABASE_DSN error")
	}
}
```

这段测试的执行过程是：

1. `t.Setenv` 只为当前测试进程设置变量，测试结束后 Go 会恢复原值，因此不会污染你的系统设置。
2. 把 `DATABASE_DSN` 主动设为空，是在模拟“部署时忘记配置数据库”的情况。
3. 调用 `Load()`，期望它立即拒绝启动条件，而不是返回一个带空 DSN 的配置。
4. `err == nil` 代表配置层放过了错误，所以测试必须失败。

为什么先测这个失败分支：缺少 DSN 时越早失败，错误越接近根因。如果让程序继续启动，错误会延迟到数据库查询时才出现，排查时很容易误以为是网络或 SQL 问题。

先运行并确认失败：

```powershell
go test ./internal/config -v
```

## 3. 写最小配置加载

规则固定为：

| 变量 | 开发默认值 | 是否必填 |
|---|---|---|
| `APP_ENV` | `development` | 否 |
| `PORT` | `8080` | 否 |
| `DATABASE_DSN` | 无 | 是 |

`Load()` 只负责读取和校验，不负责自动读取 `.env` 文件。这样运行行为更明确，Compose、PowerShell 或部署平台负责注入环境变量。

这里刻意没有引入自动读取 `.env` 的第三方包，原因是：

- Go 程序只需要认识“环境变量”，不需要知道变量来自文件、Compose 还是云平台。
- 测试可以使用 `t.Setenv`，不依赖磁盘上的某个隐藏文件。
- 生产环境通常由部署平台注入密钥，服务器上未必存在 `.env`。

代价是本地开发时需要手动设置变量，或者让 Compose 使用 `.env` 做插值。这个取舍让运行来源更明确，也减少了一个首版依赖。

本地 PowerShell 示例：

```powershell
$env:APP_ENV = 'development'
$env:PORT = '8080'
$env:DATABASE_DSN = 'blog:blog_dev_password@tcp(127.0.0.1:3307)/blog?parseTime=true&charset=utf8mb4&loc=UTC'
go run ./cmd/server
```

PowerShell 中 `$env:NAME = 'value'` 只影响当前终端进程和它启动的子进程。关掉这个终端后不会永久写入系统，这正适合临时开发配置。

执行 `go run` 时，数据流是：

```text
PowerShell 环境变量
  -> Go 进程的 os.Getenv/os.LookupEnv
  -> config.Load()
  -> Config
  -> main 组装服务器
```

## 4. 创建 `.env.example`

仓库根目录创建：

```dotenv
APP_ENV=development
PORT=8080
MYSQL_DATABASE=blog
MYSQL_USER=blog
MYSQL_PASSWORD=blog_dev_password
MYSQL_ROOT_PASSWORD=root_dev_password
MYSQL_HOST_PORT=3307
DATABASE_DSN=blog:blog_dev_password@tcp(127.0.0.1:3307)/blog?parseTime=true&charset=utf8mb4&loc=UTC
```

这些是开发示例，不是生产密钥。真实 `.env` 必须加入 `.gitignore`。

`.env.example` 的作用不是让程序自动读取，而是告诉新开发者“启动项目需要哪些变量”。真正的 `.env` 会包含个人密码，因此必须忽略。

还要区分两类变量：

- `MYSQL_DATABASE`、`MYSQL_USER` 等主要供 Compose 创建 MySQL 容器。
- `DATABASE_DSN` 供 Go 程序连接已经存在的数据库。

它们描述的是同一套连接信息，但使用者不同。后续修改账号时必须保持一致，否则 MySQL 创建了 A 用户，Go 却拿 B 用户去连接。

## 5. 使用 `log/slog`

Go 标准库已经提供结构化日志，不需要先引入第三方日志框架。

建议规则：

- 开发环境使用 `slog.NewTextHandler`，方便阅读。
- 生产环境使用 `slog.NewJSONHandler`，方便日志系统解析。
- 记录 `environment`、`port` 等非敏感字段。
- 不记录完整 `DATABASE_DSN`、密码、Cookie 或 Token。

启动日志示例：

```go
logger.Info("server starting",
	"environment", cfg.Environment,
	"port", cfg.Port,
)
```

不要这样写：

```go
logger.Info("database config", "dsn", cfg.DatabaseDSN)
```

DSN 中含有用户名和密码。

### 为什么结构化日志比拼字符串更合适

普通日志经常写成：

```go
log.Printf("server starting env=%s port=%s", cfg.Environment, cfg.Port)
```

人能读，但日志系统只能把整行当字符串。`slog` 把字段保持为键值：

```text
message = server starting
environment = development
port = 8080
```

以后可以直接筛选 `environment=production`，不用解析字符串。开发环境用 TextHandler 是为了阅读，生产使用 JSONHandler 是为了机器处理；业务含义没有变化。

### 不这样做会出现什么

| 写法 | 可能结果 |
|---|---|
| 在源码写死 DSN | 提交代码时一起泄露密码；换环境必须重新改代码 |
| 缺少 DSN 仍继续启动 | 错误延迟到数据库操作，定位困难 |
| 每个包自行 `os.Getenv` | 默认值和校验规则逐渐不一致 |
| 把完整 Config 直接打印 | DSN、Cookie 或未来的 OAuth Secret 进入日志 |
| 测试直接修改系统环境 | 一个测试影响另一个测试，结果不稳定 |

## 5.1 最小练习

在不看上文的情况下回答并实践：

1. 把 `PORT` 临时改为 `9090`，预测 `go run ./cmd/server` 应监听哪里。
2. 删除当前终端的 `DATABASE_DSN`，预测 `Load()` 返回什么。
3. 给 `Config` 增加 `LogLevel` 前，先写一个“未设置时默认 info”的测试。
4. 检查日志输出，确认其中没有 `blog_dev_password`。

练习的重点不是多加字段，而是重复“先决定规则 → 写失败测试 → 实现规则”的过程。
