# 08 · 前后端最小测试

目标：**让 Go 和 React 都有会真正执行的测试，而不只是“构建没报错”。**

## 本篇要改变的不是命令，而是开发顺序

没有测试时，常见顺序是：

```text
写实现 -> 浏览器点一下 -> 觉得能用 -> 继续堆功能
```

问题是几天后修改另一处代码，你已经不知道该重新手点哪些页面。Phase 01 建立的顺序是：

```text
描述期望行为
  -> 写测试
  -> 看到测试因缺少行为而失败
  -> 写最小实现
  -> 看到测试通过
  -> 再运行完整测试和构建
```

“先失败”不是形式主义。它证明测试真的能发现功能缺失；如果实现前测试就通过，测试可能断言错了东西。

## 1. 构建与测试的区别

```text
构建通过：语法和类型基本正确，能生成程序。
测试通过：指定输入得到了期望行为。
```

当前 `go test ./...` 显示 `[no test files]`，命令退出成功，但没有验证任何业务行为。

Phase 01 结束时至少要有：

- 配置加载测试。
- Router/健康检查测试。
- 数据库失败测试。
- React 最小渲染测试。

这些测试形成三个层次：

- 纯配置测试：速度快，验证输入如何变成配置。
- HTTP Handler/Router 测试：验证状态码和 JSON，不启动真实端口。
- React 组件测试：验证用户能看到的界面和交互。

MySQL 容器联调留在下一篇，它属于更慢的集成验证，不能替代这些快速测试。

## 2. Go 测试组织

推荐就近放置：

```text
internal/config/config.go
internal/config/config_test.go

internal/health/handler.go
internal/health/handler_test.go

internal/server/router.go
internal/server/router_test.go
```

Go 的 `_test.go` 只在 `go test` 时编译，不会进入生产二进制。

为什么测试就近放：阅读 `config.go` 时马上能找到它的行为约束；移动一个 package 时测试一起移动。不要把所有测试堆到一个远离源码的巨大目录。

Go 测试函数需要：

```text
文件名：*_test.go
函数名：TestXxx
参数：  t *testing.T
```

`go test ./...` 中的 `./...` 表示递归测试当前 module 的所有 package，而不是只测试当前目录。

运行全部测试：

```powershell
cd backend
go test ./...
```

需要查看具体测试名：

```powershell
go test ./... -v
```

竞态检查可在当前阶段加入：

```powershell
go test -race ./...
```

如果 Windows 环境的 race 构建受到 CGO 工具链限制，记录真实错误，不把它伪装成业务测试失败。

Race Detector 检查多个 goroutine 对共享内存的不安全访问。它比普通测试更慢，而且依赖平台工具链，所以属于额外验证；不能因为本机工具链不支持就说普通测试也失败，也不能在未运行时声称竞态检查通过。

## 3. 前端安装 Vitest

在 `frontend/` 中：

```powershell
npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event
```

这些依赖分别负责：

- `vitest`：测试运行器。
- `jsdom`：在 Node 环境模拟浏览器 DOM。
- `@testing-library/react`：按用户看到的内容测试组件。
- `jest-dom`：提供更易读的 DOM 断言。
- `user-event`：模拟用户点击和输入。

为什么不直接用 `document.querySelector`：Testing Library 鼓励通过角色、可访问名称和可见文本寻找元素。这样测试更接近真实用户和辅助技术的使用方式，也会推动页面使用正确的 button、heading、label 语义。

`user-event` 比直接触发单个 DOM event 更接近浏览器行为，例如一次输入通常会产生 focus、keydown、input 等多个事件。

## 4. 增加测试脚本

`frontend/package.json`：

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

保留已有的 `dev`、`build`、`lint` 和 `preview`。

为什么同时保留 `test` 和 `test:watch`：

- `test` 单次运行并退出，适合 CI 和阶段验收。
- `test:watch` 在本地持续监听文件，适合边写边反馈。

验收文档必须使用会退出的 `npm run test`，否则自动流程会一直等待。

## 5. 测试环境配置

可以在 `vite.config.ts` 中加入测试配置，或者单独建立 `vitest.config.ts`。首版保持最小，使用与 Vite 相同的 React 插件即可。

测试环境目标：

```text
environment: jsdom
setupFiles: ./src/test/setup.ts
```

- `jsdom` 给 Node 提供 `document`、`window` 等浏览器对象，但它不是完整浏览器。
- `setupFiles` 在每个测试文件前加载共同配置，避免每个文件重复 import jest-dom。
- CSS 布局、真实网络、浏览器导航和像素渲染不应该只依赖 jsdom 判断；它们属于后续 Playwright/E2E 范围。

`src/test/setup.ts`：

```ts
import '@testing-library/jest-dom/vitest'
```

## 6. 写最小烟雾测试

当前 App 仍是 Vite 起始页面，因此测试现有可见文本即可：

```text
frontend/src/App.test.tsx
```

```tsx
import { render, screen } from '@testing-library/react'
import { describe, expect, it } from 'vitest'
import App from './App'

describe('App', () => {
  it('renders the starter heading', () => {
    render(<App />)
    expect(screen.getByRole('heading', { name: 'Get started' })).toBeInTheDocument()
  })
})
```

逐行理解：

- `render(<App />)` 把组件挂到 jsdom。
- `getByRole('heading', { name: 'Get started' })` 按“标题角色 + 可见名称”查找。
- 找不到时 `getByRole` 会直接抛错，测试失败。
- `toBeInTheDocument()` 判断该元素确实位于当前 DOM 中。

为什么不测试组件内部 state 变量：用户看不到 `count` 变量，只能看到按钮文字和点击后的变化。测试可观察行为，重构内部实现时才不会无意义地大量改测试。

先运行测试。若配置尚未完成，它应该因缺少 jsdom/setup 或断言扩展而失败；补齐最小配置后再运行到通过。

这个测试以后可以随着首页重做而替换，它现在的价值是证明测试链路正常。

## 7. 最终验证命令

```powershell
cd backend
go test ./...
go build ./...

cd ..\frontend
npm run test
npm run lint
npm run build
```

所有命令都必须实际执行并查看退出码。

推荐把失败分成三类：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 测试断言失败 | 预期 200，实际 503 | 检查行为或断言是否符合规格 |
| 测试环境失败 | jsdom 未配置、包找不到 | 修复测试工具配置 |
| 构建失败 | TypeScript/Go 编译错误 | 修复类型、import 或生成代码 |

不要为了变绿而删除断言。先判断失败是在告诉你产品行为错误，还是测试环境尚未准备好。

## 7.1 最小练习

1. 故意把标题断言改成不存在的文字，观察 Testing Library 错误如何展示可访问角色。
2. 在实现 `NewRouter` 前运行测试，记录失败；实现后再次运行并对比。
3. 解释为什么 `go build` 成功不能证明数据库失败时返回 503。
4. 给当前计数按钮补一个点击测试，但只断言用户可见文本，不读取组件内部 state。
