# 07 · 健康检查

目标：**区分“Go 进程还能响应”和“服务已经能正常访问 MySQL”。**

## 本篇先看一个错误设计会怎样

假设健康检查只有一个 `/health`，并且每次都检查数据库。当 MySQL 短暂重启时：

```text
MySQL 暂时不可用
  -> /health 失败
  -> Docker/Kubernetes 判断 Go 已死亡
  -> 重启 Go
  -> Go 重启后 MySQL 仍在恢复
  -> /health 再次失败
  -> 不断重启
```

Go 进程原本没有坏，却因为把“依赖暂时不可用”和“进程死亡”混成一个信号而进入重启循环。Liveness 与 Readiness 分开，就是为了让运维系统采取不同动作。

```text
Liveness 失败  -> 进程可能卡死，需要重启
Readiness 失败 -> 暂时不要把业务流量交给它
```

## 1. 两种健康状态

### Liveness：进程活着吗

只要 Gin 可以处理请求就返回成功。数据库临时断开时，进程仍然活着，不应该因为 liveness 失败被无限重启。

```text
GET /api/health/live
```

### Readiness：服务可用吗

只有数据库 Ping 成功才返回 200。部署系统可以据此判断是否应该把请求发送给当前实例。

```text
GET /api/health/ready
```

现有调用继续使用：

```text
GET /api/health
```

兼容接口表示整体就绪状态，与 ready 使用相同检查。

为什么保留 `/api/health`：前端 Nginx、已有文档或人工检查已经使用这个地址。重构时保留兼容入口，可以避免一次目录调整顺带破坏外部调用。等所有调用方迁移后，再单独决定是否删除。

## 2. 用小接口隔离数据库

Handler 不需要知道 MySQL 的所有方法，只需要“能不能 Ping”：

```go
type Checker interface {
	PingContext(ctx context.Context) error
}
```

`*sql.DB` 本身满足这个接口。测试时则传入一个假的 Checker，不需要真的启动 MySQL。

这是有实际价值的最小接口，不是为了分层而分层。

Go 的接口是隐式实现：`*sql.DB` 只要拥有签名相同的 `PingContext`，就自动满足 `Checker`，不需要写 `implements`。

为什么 Handler 不直接接收 `*sql.DB`：

- Handler 真正需要的只有 Ping 能力。
- 接收整个 `*sql.DB` 会让测试不得不准备真实数据库或复杂 mock。
- 小接口把依赖缩小到一个方法，失败分支可以用十几行 fake 精确模拟。

如果以后数据库层更换，只要新类型仍能实现 `PingContext`，健康 Handler 不需要知道内部变化。

## 3. 先写失败测试

目标文件：

```text
backend/internal/health/handler_test.go
```

测试至少覆盖：

1. live 始终返回 200。
2. Checker 返回 nil 时 ready 返回 200。
3. Checker 返回错误时 ready 返回 503。
4. 失败响应不暴露数据库密码或 DSN。

假的 Checker 可以写成：

```go
type fakeChecker struct {
	err error
}

func (f fakeChecker) PingContext(context.Context) error {
	return f.err
}
```

这个 fake 没有“假装实现数据库”。它只实现测试需要的一个行为：

- `err == nil`：模拟数据库可用。
- `err != nil`：模拟数据库失败。

因此测试关注的是 Handler 如何把依赖结果映射成 HTTP，而不是重复测试 MySQL 自己会不会 Ping。

先运行：

```powershell
go test ./internal/health -v
```

确认因 Handler 尚不存在而失败。

## 4. 最小响应约定

live 成功：

```json
{
  "status": "ok"
}
```

ready 成功：

```json
{
  "status": "ok",
  "database": "ok"
}
```

ready 失败：

```json
{
  "status": "unavailable",
  "database": "unavailable"
}
```

HTTP 状态为 `503 Service Unavailable`。内部错误写入服务端日志，响应中不要把 `dial tcp`、用户名、密码和 DSN 返回前端。

为什么使用 503 而不是 500：500 表示请求处理出现未预期错误；503 明确表达“服务当前暂时不能接收业务流量，稍后可能恢复”。监控与代理可以据此做更合理的重试和摘流。

响应只给稳定状态字段，详细错误写日志。否则 MySQL 驱动错误可能把主机、端口甚至 DSN 片段暴露给公网访客。

## 5. Router 如何注册

目标接口：

```go
func NewRouter(checker health.Checker) *gin.Engine
```

路由：

```text
GET /api/health/live
GET /api/health/ready
GET /api/health
```

`cmd/server/main.go` 先用 `OpenMySQL` 得到 `*sql.DB`，再传给 `NewRouter(db)`。

请求执行链路：

```text
GET /api/health/ready
  -> Gin Router
  -> health Handler
  -> 创建 2 秒 Context
  -> Checker.PingContext
  -> *sql.DB 从连接池验证连接
  -> Handler 根据 error 返回 200 或 503
```

## 6. 超时

每次 readiness Ping 都必须设置短超时，例如 2 秒。数据库失联时不能让健康请求无限挂起。

```go
ctx, cancel := context.WithTimeout(c.Request.Context(), 2*time.Second)
defer cancel()
```

`context.WithTimeout` 返回新 Context 和取消函数：

- 新 Context 最多存活 2 秒。
- 数据库提前返回时，`defer cancel()` 立即释放定时器资源。
- 超时后驱动收到取消信号，Handler 不必无限等待。

为什么沿用 `c.Request.Context()` 作为父 Context：如果客户端已经断开连接，上游取消可以继续传到数据库操作，避免做没人等待的工作。

### 常见错误

| 写法 | 后果 |
|---|---|
| live 也 Ping MySQL | 数据库故障触发 Go 重启循环 |
| ready 永远返回 200 | 流量继续进入不可用实例 |
| 没有超时 | 网络故障时健康请求长期挂起 |
| 把 `err.Error()` 返回 JSON | 暴露内部网络和连接信息 |
| Handler 直接创建数据库连接 | 每个请求重复组装依赖，难以测试和复用 |

## 6.1 最小练习

1. 让 fake Checker 返回 `errors.New("mysql down")`，预测状态码和响应体。
2. 给 fake 增加调用次数，证明一次 ready 请求只 Ping 一次。
3. 思考：如果 Redis 以后也是必需依赖，ready 应怎样组合多个检查？先写答案，不急着实现。
4. 停掉 MySQL 后比较 live 与 ready，解释为什么结果不同才是正确行为。
